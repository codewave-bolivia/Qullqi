# Research: Local Data Layer — Identity and Verification Model

## R1. SQLDelight version and toolchain compatibility

- **Decision**: SQLDelight **2.4.1** (latest release, 2026-10-06).
- **Evidence**: throw-away spike (clone outside the repository, 2026-11-13) with the real toolchain
  — Kotlin 2.4.21, AGP 9.1.1 with `com.android.kotlin.multiplatform.library`, Gradle 9.5.1, JDK 21.
  `:shared:compileAndroidMain`, `:shared:compileKotlinJvm` and `:shared:testAndroidHostTest` passed;
  code generated for `QullqiDatabase`; 1 test, 0 failures. The spike confirmed: seed `INSERT` runs
  in `Schema.create`, partial unique index rejects a second open attempt, FK rejects an orphan,
  `CHECK (slot = 1)` rejects a second session row.
- **Not verifiable on Linux**: iOS compilation (`compileKotlinIosArm64` is skipped on this host).
- **Alternatives**: Room KMP (would contradict constitution v1.1.0, which mandates SQLDelight).

## R2. Platform drivers without touching Builder-owned source sets

- **Decision**: no `expect fun createDriver()`. `DatabaseFactory.create(driver: SqlDriver)` lives in
  `commonMain`; `AndroidDatabaseFactory` (androidMain) builds an `AndroidSqliteDriver` and enables
  foreign keys in `onConfigure`. iOS (`NativeSqliteDriver`) and Desktop (`JdbcSqliteDriver`) factories
  are left to the Builder.
- **Rationale**: an `expect` declaration requires `actual`s in `iosMain` and `jvmMain`, which are
  protected; without them the jvm/iOS targets would not compile and the PR check would fail.
- **Alternatives**: `expect`/`actual` (needs protected files); a Koin module (DI library needs an
  amendment).

## R3. Foreign keys per connection

- **Decision**: `DatabaseFactory.create` executes `PRAGMA foreign_keys = ON` before returning;
  `AndroidDatabaseFactory` also sets it in `onConfigure` (Android may open new connections).
  Tests use the same `DatabaseFactory`, so tests exercise the real setting.
- **Rationale**: SQLite disables FK enforcement by default (CLAUDE.md §14.2).

## R4. PIN protection (FR-004, SC-007)

- **Decision**: `PinHasher` interface in `domain/security`; Android implementation
  `PBKDF2WithHmacSHA256`, 16-byte salt from `SecureRandom`, 120 000 iterations, 32-byte output,
  stored as base64 with salt and iteration count. Constant-time comparison.
- **Rationale**: no crypto in Kotlin common stdlib; `javax.crypto` is available on Android and on the
  JVM used by host tests, so no new dependency.
- **Known ceiling**: a 4-digit PIN has 10 000 combinations; any offline hash is brute-forceable by
  someone with the database file. The real protection is the 3-attempt lock plus app-private storage.
  Upgrade path when real data exists: wrap with an Android Keystore key (hardware-backed). Marked
  with a `ponytail:` comment in code.
- **Seed hashes**: precomputed with the same parameters and fixed salts so sample users can log in
  with the documented sample PIN; values generated by a script, never hand-typed.
- **Alternatives**: kotlincrypto/cryptography-kotlin (new dependency, approval needed); SHA-256
  without salt (trivially reversible table).

## R5. "Exactly one open session" and "one non-final attempt"

- **Decision**: `current_session` with `slot INTEGER PRIMARY KEY CHECK (slot = 1)` (logout deletes
  the row; login does `INSERT OR REPLACE`). Partial unique index
  `ON kyc_attempt(user_id) WHERE state IN ('DRAFT','SUBMITTED')`.
- **Rationale**: both rules enforced by the store (FR-021) with no extra code; spike verified both.
- **Alternatives**: session history table with `closed_at` (history not required by the spec).

## R6. Keeping verification status consistent (FR-016)

- **Decision**: `AFTER UPDATE OF state ON kyc_attempt` trigger that, when the new state is final,
  sets `user.verification` (`APPROVED→VERIFIED`, `REVIEW→UNDER_REVIEW`, `REJECTED→NOT_VERIFIED`).
  Repository still wraps submit+process in a transaction.
- **Rationale**: a single source of truth for the rule, impossible to bypass from Kotlin.

## R7. Mock processing outcome (FR-018)

- **Decision**: `MockKycProcessor` decides by the last digit of the document number:
  `0` → rejected (reason "Documento ilegible"), `5` → under review, anything else → approved.
  Processing takes 4 steps × 700 ms (reference documentation), skippable in tests via injected delay.
- **Rationale**: testers choose the outcome just by typing a number; reproducible.

## R8. Phone confirmation in sample mode (FR-011)

- **Decision**: `OtpCodeGenerator` interface; sample implementation always returns `123456`.
  Resend window 30 s, validity 5 min, 3 tries, computed from the injected `Clock`.
- **Rationale**: no SMS without backend; deterministic tests.

## R9. Identifiers and time

- **Decision**: `UserId` and attempt ids are `TEXT`. Seed uses readable fixed ids (`usr-verified`, …);
  runtime ids come from an injected `IdGenerator` (default `kotlin.uuid.Uuid.random()`).
  Instants as epoch ms from an injected `Clock`.
- **Rationale**: stable ids for the M4 contract (FR-026); deterministic tests.

## R10. Image references (FR-019)

- **Decision**: image columns accept only references with prefix `placeholder:`
  (`CHECK (front_ref IS NULL OR front_ref LIKE 'placeholder:%')`, same for back/selfie). Bundled
  placeholder assets belong to M3 UI; this feature defines the reference names:
  `placeholder:ci-front`, `placeholder:ci-back`, `placeholder:passport`, `placeholder:selfie`.
- **Rationale**: makes storing a real capture impossible at the store level.
